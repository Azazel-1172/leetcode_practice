# 1658. 将 x 减到 0 的最小操作数

## 題目

给你一个整数数组 `nums` 和一个整数 `x` 。每一次操作时，你应当移除数组 `nums` 最左边或最右边的元素，然后从 `x` 中减去该元素的值。请注意，需要 **修改** 数组以供接下来的操作使用。

如果可以将 `x` **恰好** 减到 `0` ，返回** 最小操作数 **；否则，返回 `-1` 。

 

**示例 1：**

```

**输入：**nums = [1,1,4,2,3], x = 5
**输出：**2
**解释：**最佳解决方案是移除后两个元素，将 x 减到 0 。
```

**示例 2：**

```

**输入：**nums = [5,6,7,8,9], x = 4
**输出：**-1
```

**示例 3：**

```

**输入：**nums = [3,2,20,1,1,3], x = 10
**输出：**5
**解释：**最佳解决方案是移除后三个元素和前两个元素（总共 5 次操作），将 x 减到 0 。
```

 

**提示：**

- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^4`
- `1 <= x <= 10^9`

## 白話翻譯

- **輸入**：一個全是正數的陣列 `nums`，和一個目標數 `x`
- **每一步**：從陣列最左邊或最右邊拿掉一個數，`x` 減掉這個數
- **答案**：讓 `x` 剛好變成 0 的**最少**步數，做不到就回傳 `-1`

**換個角度看**：不管拿的順序是什麼，最後被拿走的一定是「一段前綴 + 一段後綴」，留下來的是**中間一段連續子陣列**。所以題目等於在問：

> 在原陣列裡找一段連續子陣列，總和剛好是 `sum(nums) − x`，而且**長度最長**。答案 = `n − 最長長度`。

## 解題筆記

### 思路

#### 1. 第一直覺：決策樹
每一步都能選「拿左」或「拿右」，畫出來是一棵二元樹，用 DFS/BFS 走一定找得到答案（BFS 第一次碰到 x == 0 的那一層就是最少步數）。

但樹的**深度**最多是 n，節點數約 **2ⁿ**。n = 10⁵ 時一定超時。

> 一開始誤以為節點數是 log(n)，那其實是「n 個節點的平衡樹」的高度，這裡剛好反過來。

#### 2. 縮減狀態：(i, j)
「先左後右」和「先右後左」剩下的陣列一樣，很多節點是重複的。只要知道「左邊拿了 i 個、右邊拿了 j 個」，剩下的 x 和操作次數都算得出來，所以狀態就是 `(i, j)`。

限制 `i + j ≤ n`，狀態數約 n²/2，從指數降到 O(n²)。但 10¹⁰ 還是太大。

#### 3. 關鍵轉換：看「留下的」而不是「拿走的」
被拿走的 = 前綴 + 後綴，留下的 = **中間一段連續子陣列**。

```
nums:  [ 拿走 | 拿走 | 留下 留下 留下 | 拿走 ]
          前綴          中間連續段      後綴
```

推導 target：

```
sum(nums) = 拿走的總和 + 留下的總和
拿走的總和 = x                ← 「成功」的定義就是 x 剛好扣到 0
=> 留下的總和 = sum(nums) − x = target
```

- `sum(nums)` 是**原陣列**的總和，nums 從頭到尾沒被改動；target 是一個**數字**，不是陣列
- 這不是保證一定拿得掉 x，而是「**如果**某種拿法成功，它留下的那段總和**必定**是 target」。找不到這樣的一段，就代表沒有成功的拿法，回傳 `-1`
- 操作最少 ⟺ 拿走最少 ⟺ 留下的**最長**

問題變成：**找總和剛好 = target 的最長連續子陣列**。

#### 4. 滑動窗口
列舉每個結尾 `right`，找以它結尾、總和 = target 的那段。因為**全是正數**：
- 固定 `right`，`left` 越往右總和越小，符合條件的 `left` 最多一個
- `right` 右移，總和只會變大，合適的 `left` 只會往右、不會往左

所以走法固定：

| 狀況 | 動作 |
|---|---|
| 每一輪 | `right` 右移，把 `nums[right]` 加進窗口 |
| `windowSum > target` | `left` 右移，直到 `windowSum ≤ target` |
| `windowSum == target` | 記錄長度 `right − left + 1`，**繼續找**（可能還有更長的） |

兩個指標都只往右走，各最多 n 步 → O(n)。

用示例 3 跑一次（`sum = 30`、`x = 10`、`target = 20`）：

| right | 加入 | 收縮 left | 窗口 | 總和 | == 20？ |
|---|---|---|---|---|---|
| 0 | 3 | — | [3] | 3 | |
| 1 | 2 | — | [3,2] | 5 | |
| 2 | 20 | 丟 3、丟 2 | [20] | 20 | ✅ 長度 1 |
| 3 | 1 | 丟 20 | [1] | 1 | |
| 4 | 1 | — | [1,1] | 2 | |
| 5 | 3 | — | [1,1,3] | 5 | |

最長 1，答案 = 6 − 1 = 5。

#### 5. 邊界
- `target < 0`：`sum(nums) < x`，全部拿光也扣不完 → `-1`
- `target == 0`：`sum(nums) == x`，只能全部拿光（留下的長度 0）→ 答案 `n`。要注意滑動窗口能不能自然處理「長度 0」這個情況

### 複雜度

- 時間：O(n)
  - 算 `sum(nums)` 掃一次：O(n)
  - 滑動窗口：外層 `right` 走 n 步；內層收縮的 `left` 從不回頭，**整個過程加起來**最多也只走 n 步，總共最多 2n 次移動（攤銷分析），不是 O(n²)
- 空間：O(1)，只用 `left`、`right`、`windowSum`、`maxLen` 幾個變數

### 踩到的坑

- **樹的節點數估錯**：誤以為是 log(n)。每一層都分兩支、深度到 n，節點數是 2ⁿ
- **「區段最大值」講不清楚**：要最大化的是**長度**，總和已經被固定成剛好等於 target
- **以為左右指標都可以動**：數學上從哪邊縮總和都會變小，但滑動窗口的走法是固定的，`right` 負責擴張、`left` 負責收縮，兩者都不回頭，才能做到 O(n)
- **窗口長度少算 1**：`[left, right]` 兩端都包含，長度是 `right − left + 1`
- **找到一個解就停**：要繼續掃，因為後面可能有更長的窗口
- **把 target 當成每一步都會變的值**：`target = sum(nums) − x` 一開始算一次就固定，它是「所有成功拿法都必須滿足的條件」，不是某種拿法算出來的結果
- **以為 `sum(nums)` 是移除前後綴之後的總和**：它一直是原陣列的總和
- **以為「全部總和 == 拿走的總和」不可能**：題目允許全部拿光，此時留下的是空陣列，答案是 `n`
- **以為 `target < 0` 還有機會**：全拿都不夠，其他拿法只會拿更少，直接回傳 `-1`


## 面試官問答

### 1. 題目問的是「從兩端拿」，為什麼程式裡找的卻是「中間一段」？直接模擬左右拿的決策樹不行嗎？

<details>
<summary>參考答案</summary>

決策樹每步分兩支、深度可達 n，節點數約 2ⁿ；就算合併重複狀態成 `(i, j)`，也還有約 n²/2 個狀態，n = 10⁵ 時約 5×10⁹，一樣太慢。
觀察到不管順序，拿走的一定是「前綴 + 後綴」，留下的是中間連續一段；成功時拿走總和為 `x`，所以留下總和必為 `sum − x`。
「操作最少」等價於「留下最長」，問題就變成找總和剛好為 `target` 的最長子陣列，可以 O(n) 解。

</details>

### 2. 這個滑動窗口依賴哪個題目條件？如果 `nums` 裡可以有 0 或負數，解法要怎麼改？

<details>
<summary>參考答案</summary>

依賴 `1 <= nums[i]`：全是正數，擴張 `right` 總和一定變大、收縮 `left` 總和一定變小，所以超過 `target` 時只要動 `left` 就對。
有 0 時單調性變成「不減」，這個寫法其實還是對的；但有負數時，總和超過 `target` 不代表要收縮（後面可能有負數拉回來），窗口就失效。
改用前綴和 + 雜湊表：記錄每個前綴和**第一次**出現的位置，對每個 `i` 查 `prefix[i] − target` 是否出現過，取最長。時間 O(n)、空間 O(n)。

</details>

### 3. 外層 `for` 裡面還有一個 `while`，為什麼時間複雜度是 O(n) 而不是 O(n²)？

<details>
<summary>參考答案</summary>

`while` 每跑一次 `left` 就加 1，而 `left` 從不往回走、最多走到 `n`，所以**整個演算法**裡 `while` 的總執行次數最多 n 次。
外層 `right` 走 n 次，加上算 `sum` 的 n 次，總共 O(n)，這是攤銷分析。

</details>

### 4. 對某個 `right`，窗口收縮完只檢查了一個 `left`。為什麼不會漏掉以 `right` 結尾、總和也等於 `target` 的其他窗口？

<details>
<summary>參考答案</summary>

不變量：收縮後 `left` 是讓 `sum(nums[left..right]) <= target` 的**最小**索引。
因為全是正數，以 `right` 結尾的窗口總和隨起點右移嚴格遞減，總和剛好等於 `target` 的起點最多只有一個；比 `left` 更左的起點總和都 > `target`，更右的都 < `left` 的總和。
所以若存在答案，一定就是 `left`。而 `right` 右移時合適的起點只會往右，`left` 不用回頭重找。

</details>

### 5. `maxLen` 為什麼初始化成 `-1` 而不是 `0`？`target == 0` 的情況程式怎麼處理？

<details>
<summary>參考答案</summary>

長度 0 是合法答案（`sum(nums) == x`，全部拿光，答案是 `n`），所以要用 `-1` 代表「沒找到」。若初始化成 0，示例 2（`target = 31`，沒有窗口符合）會錯誤回傳 `5 − 0 = 5`。
`target == 0` 時，每加入一個正數就被收縮成空窗口（`left == right + 1`），`windowSum == 0` 成立，長度 `right − left + 1 = 0`，不用另外寫特例。

</details>

### 6. `if (target < 0) return -1;` 拿掉會怎樣？C++ 和 JS 的結果一樣嗎？

<details>
<summary>參考答案</summary>

`target < 0` 時空窗口總和 0 仍 > `target`，`while` 會讓 `left` 一路超過 `right`，讀到 `nums[n]`。
C++ 是越界存取，未定義行為。JS 讀到 `undefined`，`windowSum` 變成 `NaN`，`NaN > target` 為 `false` 讓迴圈停下，之後所有比較都是 `false`，最後剛好回傳 `-1`（實測 `[1,1]` / `x = 5` 回傳 `-1`、`windowSum` 為 `NaN`）。
JS 是碰巧答對，不能依賴，提早回傳才是正確寫法。

</details>

### 7. C++ 版本全用 `int`，會不會溢位？

<details>
<summary>參考答案</summary>

`sum(nums)` 最大 10⁵ × 10⁴ = 10⁹，`int` 上限 2³¹ − 1 ≈ 2.147×10⁹，裝得下。
`target = total − x` 範圍在 [−10⁹, 10⁹]；`windowSum` 在加入新元素後最大為 `target + 10⁴`，也都在範圍內。
若題目放寬到 `nums[i] <= 10⁵` 之類，總和會到 10¹⁰，就要改用 `long long`。JS 的 `number` 在 2⁵³ 以內整數都精確，不用擔心。

</details>

### 8. 官方標籤有「二分搜尋」和「雜湊表」，那兩種解法跟滑動窗口相比有什麼取捨？

<details>
<summary>參考答案</summary>

- **前綴和 + 二分搜尋**：全是正數所以前綴和嚴格遞增；列舉從右邊拿幾個，在前綴和上二分搜尋剛好補足 `x` 的左邊長度。時間 O(n log n)、空間 O(n)。
- **前綴和 + 雜湊表**：O(n) 時間、O(n) 空間，而且**不需要正數條件**。
- **滑動窗口**：O(n) 時間、O(1) 空間，最省，但只在正數時成立。

這題條件保證正數，所以滑動窗口最好；題目若可能有負數，就要換雜湊表。

</details>

### 9. 變形：如果改成「讓 `x` 減到**小於等於** 0 的最小操作數」，要怎麼改？

<details>
<summary>參考答案</summary>

拿走總和 `>= x` ⟺ 留下總和 `<= target`，改成找「總和 `<= target` 的最長子陣列」。
程式幾乎不變：收縮完 `windowSum <= target` 一定成立，所以每個 `right` 都直接更新 `maxLen = max(maxLen, right − left + 1)`，不用判斷相等。
`target < 0` 仍回傳 `-1`；`target >= 0` 時一定有解（至少空窗口可行）。

</details>

### 10. 時間複雜度還能比 O(n) 更快嗎？

<details>
<summary>參考答案</summary>

不能，下界是 Ω(n)。任何演算法都必須讀過每個元素：如果某個 `nums[i]` 沒被讀，對手可以改動它的值，讓 `sum(nums)` 改變，進而讓答案從可行變成 `-1`（或反過來），演算法卻無法察覺。
光是算 `sum(nums)` 就要 n 次讀取，現在的 O(n) 已經到頂，只剩常數差異。

</details>

### 11. 空間還能再壓嗎？

<details>
<summary>參考答案</summary>

不能再降。輸出只有一個整數，輔助空間只有 `total`、`target`、`left`、`windowSum`、`maxLen` 幾個變數，已經是 O(1)，也沒有修改輸入陣列。
相比雜湊表或二分搜尋解法要 O(n) 存前綴和，這是這個寫法最大的優勢；再往下只剩變數重用之類的常數層級差異，沒有實際量測過，不宣稱有效能提升。

</details>
