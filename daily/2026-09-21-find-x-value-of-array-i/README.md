# 3524. 求陣列的 X 值 I

## 題目

給你一個由**正整數**組成的陣列 `nums`，以及一個**正整數** `k`。

你可以對 `nums` 執行**一次**操作：在這次操作中，你可以從 `nums` 移除任意**不重疊**的前綴（prefix）與後綴（suffix），但移除後 `nums` 必須**非空**。

你要求出 `nums` 的 **x 值**：也就是有多少種操作方式，能讓剩下元素的**乘積**除以 `k` 後*餘數*為 `x`。

回傳一個長度為 `k` 的陣列 `result`，其中 `result[x]` 就是 `nums` 對應 `0 <= x <= k - 1` 的 **x 值**。

陣列的**前綴**是指從陣列開頭開始、延伸到其中任一位置的子陣列。

陣列的**後綴**是指從陣列中任一位置開始、一路延伸到結尾的子陣列。

**注意**：這次操作所選的前綴與後綴都可以是**空的**。

 

**範例 1：**

**輸入：** nums = [1,2,3,4,5], k = 3

**輸出：** [9,2,4]

**說明：**

- 當 `x = 0` 時，所有不會把 `nums[2] == 3` 移除掉的不重疊前綴／後綴移除方式都算數。
- 當 `x = 1` 時，可行的操作有：

  - 移除空前綴與後綴 `[2, 3, 4, 5]`，`nums` 變成 `[1]`。
  - 移除前綴 `[1, 2, 3]` 與後綴 `[5]`，`nums` 變成 `[4]`。

- 當 `x = 2` 時，可行的操作有：

  - 移除空前綴與後綴 `[3, 4, 5]`，`nums` 變成 `[1, 2]`。
  - 移除前綴 `[1]` 與後綴 `[3, 4, 5]`，`nums` 變成 `[2]`。
  - 移除前綴 `[1, 2, 3]` 與空後綴，`nums` 變成 `[4, 5]`。
  - 移除前綴 `[1, 2, 3, 4]` 與空後綴，`nums` 變成 `[5]`。

**範例 2：**

**輸入：** nums = [1,2,4,8,16,32], k = 4

**輸出：** [18,1,2,0]

**說明：**

- 當 `x = 0` 時，**不會**得到 `x = 0` 的操作只有：

  - 移除空前綴與後綴 `[4, 8, 16, 32]`，`nums` 變成 `[1, 2]`。
  - 移除空前綴與後綴 `[2, 4, 8, 16, 32]`，`nums` 變成 `[1]`。
  - 移除前綴 `[1]` 與後綴 `[4, 8, 16, 32]`，`nums` 變成 `[2]`。

- 當 `x = 1` 時，唯一可行的操作是：

  - 移除空前綴與後綴 `[2, 4, 8, 16, 32]`，`nums` 變成 `[1]`。

- 當 `x = 2` 時，可行的操作有：

  - 移除空前綴與後綴 `[4, 8, 16, 32]`，`nums` 變成 `[1, 2]`。
  - 移除前綴 `[1]` 與後綴 `[4, 8, 16, 32]`，`nums` 變成 `[2]`。

- 當 `x = 3` 時，沒有任何可行的操作方式。

**範例 3：**

**輸入：** nums = [1,1,2,1,1], k = 2

**輸出：** [9,6]

 

**限制條件：**

- `1 <= nums[i] <= 10^9`
- `1 <= nums.length <= 10^5`
- `1 <= k <= 5`

## 解題筆記

### 思路
1. **「移除一個前綴和一個後綴，剩下的非空」** ＝ **留下一段連續子陣列**。
所以「有幾種操作方式」就是「有幾個非空連續子陣列」。
  ```
    題目真正在問的是：對每個 `x`，有多少個連續子陣列的乘積 % k == x。
    `x` 只是餘數，也是回傳陣列的索引，所以 `result` 長度才是 `k`。
  ```

2. **按右端點分組做遞推。** 不要想「所有子陣列」，一次只想「以第 i 格結尾的子陣列」。
dp[i] = dp[i-1] 的每個結果 × nums[i]  +  nums[i] 自己單獨一個



### 複雜度

- 時間：O(n × k)。k ≤ 5，等同線性
- 空間：O(k)。用滾動陣列，只留 `cur` 和 `next` 兩個長度 k 的陣列

會這樣做是因為算 `dp[i]` 只用得到 `dp[i-1]`，更早的再也讀不到。
若要事後檢查推導過程，可改成二維 `dp[n][k]`（空間 O(n×k)），答案一樣，除錯時好用。

### 踩到的坑

- **先對元素取餘數再相乘。** 寫成 `(r * nums[i]) % k` 的話，`nums[i]` 最大 1e9，
  在 C++ 會溢位 int。先 `v = nums[i] % k`，`r * v` 最大只有 `4 × 4 = 16`
- **答案會超過 int32。** 子陣列總數可達 `1e5 × (1e5+1) / 2 ≈ 5e9`，超過約 21 億的上限。
  C++ 官方簽名給 `vector<long long>` 就是這個原因；TS 的 number 安全整數到 2^53，沒問題
- **不能原地更新 `cur`。** 必須寫進新的 `next`。一邊讀 `cur[r]` 一邊寫 `cur[新餘數]`，
  同一輪搬過去的會被重複搬第二次
- **兩個 `+=` 不要搞混。** `next[...] += cur[r]` 是在組「這一格」的統計（不同舊餘數可能撞到
  同一個新餘數，所以要累積）；`ans[r] += cur[r]` 才是把這一格併進總帳
- 第一輪 `cur` 全 0，r 迴圈自動空轉，不需要特判 i=0

### 驗證

三個官方範例都過，另外用 `n=1e5` 全 1、`k=1` 測溢位與效能：
答案 5000050000（= 所有子陣列數），耗時 27ms。

## 面試官問答

### 1. 為什麼「移除一個前綴和一個後綴」等價於「選一段連續子陣列」？請證明兩者數量一樣多。

<details>
<summary>參考答案</summary>

前綴從索引 0 往右砍、後綴從尾端往左砍，兩段不重疊且剩下非空，中間留下的必然是一段連續元素。

反向也成立：任給一段連續子陣列 `nums[l..r]`，對應的前綴唯一是 `nums[0..l-1]`、後綴唯一是 `nums[r+1..n-1]`。所以是一一對應，數量相等，都是 `n(n+1)/2` 個。

這也給了一個免費的檢查：`sum(ans)` 必定等於 `n(n+1)/2`。

</details>

### 2. 這題的時間與空間複雜度是多少？瓶頸在哪裡？

<details>
<summary>參考答案</summary>

時間 O(n × k)：外層走過 n 個元素，每個元素內部跑兩個長度 k 的迴圈。因為 `k ≤ 5`，實際上等同 O(n)。

空間 O(k)：只有 `ans`、`cur`、`next` 三個長度 k 的陣列，與 n 無關。

瓶頸是外層那趟掃描，無法再低——每個元素至少要讀一次。所以這已經是最佳複雜度。

</details>

### 3. 為什麼 `next` 要另外開一個陣列，不能直接在 `cur` 上原地修改？

<details>
<summary>參考答案</summary>

因為讀寫會互相干擾。原地改的話，`cur[r]` 搬到 `cur[(r*v)%k]` 之後，如果目標格的索引比 `r` 大，同一輪的後續迭代會再讀到它、再搬一次，同一批子陣列被重複計算。

例如 `k=4`、`v=2`：`r=1` 把 2 個搬到 `cur[2]`，接著 `r=2` 讀 `cur[2]` 時就多讀到那 2 個。

用獨立的 `next` 可以保證整輪都是讀「上一格的狀態」，寫「這一格的狀態」，兩者不混。

</details>

### 4. 為什麼要先算 `v = nums[i] % k` 再乘，而不是直接寫 `(r * nums[i]) % k`？

<details>
<summary>參考答案</summary>

為了避免溢位。`nums[i]` 最大 10⁹，`r` 最大 4，`r * nums[i]` 可達 4×10⁹，超過 int32 上限（約 2.1×10⁹），在 C++ 會溢位成負數。

先取餘數後，`r * v` 最大只有 `4 × 4 = 16`，怎樣都安全。

數學依據是 `(a × b) % k == ((a % k) × (b % k)) % k`，先取餘不影響結果。

TypeScript/JavaScript 的 number 是雙精度浮點，安全整數到 2⁵³，不會踩到這個坑——但這是語言特性，不是解法正確，換到 C++ 或 Java 就會炸。

</details>

### 5. 回傳型別為什麼是 `vector<long long>` 而不是 `vector<int>`？

<details>
<summary>參考答案</summary>

`ans` 存的是子陣列個數，總和是 `n(n+1)/2`。`n` 最大 10⁵，算出來約 5×10⁹，超過 int32 上限。

最壞情況是所有子陣列都落在同一格（例如 `k=1`，全部餘 0），那一格就會存到 5×10⁹。

這也是為什麼測試時要特意跑 `n=1e5`、`k=1`：它同時驗證了計數正確與型別夠大。

</details>

### 6. 怎麼確定每個子陣列恰好被算一次，不重複也不遺漏？

<details>
<summary>參考答案</summary>

用**右端點**當分類依據。每個子陣列有唯一的右端點 `i`，所以按右端點分組是一個嚴格的分割——不會有子陣列同時屬於兩組，也不會有落在組外的。

第 `i` 輪算出的 `cur` 正好涵蓋所有右端點為 `i` 的子陣列（左端點 0..i 共 i+1 個，由「上一輪的 i 個」加「自己 1 個」組成）。每輪把 `cur` 累加進 `ans`，全部 n 輪加完就是全部。

驗證方式：`sum(ans) == n(n+1)/2`。

</details>

### 7. 如果 `k` 不再限制在 5 以內，而是可以到 10⁵，你的解法還能用嗎？

<details>
<summary>參考答案</summary>

複雜度會變成 O(n × k) = 10¹⁰，太慢，而且回傳陣列本身就要 10⁵ 格。

但有個關鍵觀察可以救：從某個位置往左看，所有子陣列的乘積對 k 取餘，**不同值的數量是 O(log k) 級別**的。因為每次乘進新元素，餘數要嘛不變、要嘛因為多吃進 k 的某個質因數而「往下掉」，能掉的次數受限於 k 的質因數個數。

所以可以改成維護「（餘數, 出現次數）」的清單而非完整陣列，每輪的清單長度是 O(log k)，整體降到 O(n log k)。這正是本題的進階版 Find X Value of Array II 的思路。

</details>

### 8. 如果題目改成「移除的前綴和後綴不能為空」，程式要怎麼改？

<details>
<summary>參考答案</summary>

前綴後綴都非空，等於左端點至少是 1、右端點至多是 n-2，也就是只數 `nums[1..n-2]` 範圍內的子陣列。

最小改動：把迴圈改成只走 `i` 從 1 到 n-2，並且在遞推時不要讓左端點觸及 0。實作上可以直接對子陣列 `nums.slice(1, n-1)` 跑原本的演算法。

邊界要注意：`n < 3` 時沒有任何合法操作，應回傳全 0。

</details>

### 9. 如果要求的不是乘積而是「總和」對 k 取餘，解法要怎麼調整？

<details>
<summary>參考答案</summary>

遞推式從 `(r * v) % k` 換成 `(r + v) % k`，其餘結構完全不變——因為加法同樣滿足 `(a+b) % k == ((a%k)+(b%k)) % k`。

不過總和版有更好的解法：用前綴和。`sum(l..r) % k == (pre[r] - pre[l-1]) % k`，所以只要開一個長度 k 的計數器統計每個 `pre[i] % k` 出現幾次，用組合數就能 O(n + k) 算完，不需要逐格遞推。

乘積版沒辦法這樣做，因為乘法在模 k 下不一定有反元素（`k` 不是質數、或元素與 `k` 不互質時就除不回去）。這正是乘積版比總和版難的地方。

</details>

### 10. 這題能不能比 O(n × k) 更快？理論下界是多少？

<details>
<summary>參考答案</summary>

下界是 **Ω(n + k)**：

- `Ω(n)`：必須讀過每一個元素。若有任何元素沒讀，對手可以把它改成別的值——它至少出現在一個子陣列裡，答案就會變，所以不讀不可能正確。
- `Ω(k)`：輸出本身就有 k 格，光是寫出答案就要這麼多步。

本題 `k ≤ 5`，O(n × k) 已經等同 O(n)，貼著下界，沒有優化空間。

k 很大時才有差距，這時可以改用「每個位置往左的相異餘數只有 O(log k) 種」的觀察（見第 7 題），把每輪的工作量從 k 降到 log k，總計 O(n log k)。

</details>

### 11. 空間能不能壓得比 O(k) 更低？

<details>
<summary>參考答案</summary>

要區分兩種空間：

- **輸出**：`ans` 有 k 格，這是題目要求的回傳值，無法省。
- **輔助空間**：`cur` 和 `next` 各 k 格，也就是 O(k)。

所以總空間 O(k) 已經和輸出同級，意義上就是「除了答案本身之外幾乎沒多用」。

剩下的只有微優化：迴圈內每輪 `new Array(k)` 可以改成預先配置兩個緩衝區、用 `fill(0)` 清空再互換，把配置次數從 n 次降到 2 次。

**但實測沒有好處。** 我用 n=2,000,000、k=5 跑過三種寫法（每輪 new／解構交換／暫存變數交換），多輪結果互有勝負、差異落在雜訊範圍內。原因是 k 很小時 JIT 對短命小物件的處理很有效率，而 `[cur, next] = [next, cur]` 這種解構交換反而自己會配置一個暫時陣列。

結論：這個微優化不值得做，改壞可讀性又換不到效能。**要先量測再優化。**

</details>
