# 3525. 求出数组的 X 值 II

> 英文原題：Find X Value of Array II

> 翻譯來源：leetcode.cn

## 題目

给你一个由 **正整数 **组成的数组 `nums` 和一个 **正整数** `k`。同时给你一个二维数组 `queries`，其中 `queries[i] = [index_i, value_i, start_i, x_i]`。

你可以对 `nums` 执行 **一次 **操作，移除 `nums` 的任意 **后缀 **，使得 `nums` 仍然**非空**。

给定一个 `x`，`nums` 的 **x值 **定义为执行以上操作后剩余元素的 **乘积 **除以 `k` 的 **余数 **为 `x` 的方案数。

对于 `queries` 中的每个查询，你需要执行以下操作，然后确定 `x_i` 对应的 `nums` 的 **x值**：

- 将 `nums[index_i]` 更新为 `value_i`。仅这个更改在接下来的所有查询中保留。
- **移除 **前缀 `nums[0..(start_i - 1)]`（`nums[0..(-1)]` 表示 **空前缀 **）。

返回一个长度为 `queries.length` 的数组 `result`，其中 `result[i]` 是第 `i` 个查询的答案。

数组的一个 **前缀 **是从数组开始位置到任意位置的子数组。

数组的一个 **后缀 **是从数组中任意位置开始直到结束的子数组。

**子数组 **是数组中一段连续的元素序列。

**注意**：操作中所选的前缀或后缀可以是 **空的 **。

**注意**：x值在本题中与问题 I 有不同的定义。

 

**示例 1：**

**输入：** nums = `[1,2,3,4,5]`, k = 3, queries = `[[2,2,0,2],[3,3,3,0],[0,1,0,1]]`

**输出：** `[2,2,2]`

**解释：**

nums = `[1,2,3,4,5]`, k = 3, queries = `[[2,2,0,2],[3,3,3,0],[0,1,0,1]]`

第一次 quries 後：
nums = [1,2,2,4,5] prod = [1,2,4,16,80]
找乘積 % k = 2 的前綴的子陣列數: [1,2], [1,2,2,4,5]
result = [2]

第二次 quries 後：
nums = [1,2,2,3,5] prod = [1,2,4,12,60]
找乘積 % k = 0 的前綴的子陣列數: [3], [3,5]
result = [2, 2]

第三次 quries 後：
nums = [1,2,2,3,5]   prod = [1,2,4,12,60]
乘積 % 3 == 1 的前綴：[1], [1,2,2]
result = [2, 2, 2]

**示例 2：**

**输入：** nums = `[1,2,4,8,16,32]`, k = 4, queries = `[[0,2,0,2],[0,2,0,1]]`

**输出：** `[1,0]`

**解释：**

- 对于查询 0，`nums` 变为 `[2, 2, 4, 8, 16, 32]`。唯一可行的操作是：

  - 移除后缀 `[2, 4, 8, 16, 32]`。

- 对于查询 1，`nums` 仍为 `[2, 2, 4, 8, 16, 32]`。没有任何操作能使余数为 1。

**示例 3：**

**输入：** nums = `[1,1,2,1,1]`, k = 2, queries = `[[2,1,0,1]]`

**输出：** `[5]`

 

**提示：**

- `1 <= nums[i] <= 10^9`
- `1 <= nums.length <= 10^5`
- `1 <= k <= 5`
- `1 <= queries.length <= 2 * 10^4`
- `queries[i] == [index_i, value_i, start_i, x_i]`
- `0 <= index_i <= nums.length - 1`
- `1 <= value_i <= 10^9`
- `0 <= start_i <= nums.length - 1`
- `0 <= x_i <= k - 1`

## 白話翻譯

給定正整數陣列 `nums` 和正整數 `k`。

對 `queries` 裡的每一筆 `[index, value, start, x]`：

1. `nums[index] = value` ← **永久**，之後每一筆查詢都看得到
2. 看 `nums[start..n-1]` 這段 ← **暫時**，只影響這一筆
3. 枚舉它的所有非空前綴（共 `n - start` 個）
4. 數出「乘積 % k == x」的有幾個 ← 這就是這筆的答案

回傳長度 `q` 的答案陣列。

> 題目的「移除後綴、使 nums 仍非空」＝ 枚舉前綴 `nums[start..j]`，j 從 start 到 n-1。
> 「x值」是題目自創詞，等同 `x值(陣列, k, x) = 符合「乘積 % k == x」的前綴個數`，
> 注意與問題 I 的定義不同。

## 解題筆記

### 思路

1. **先寫暴力解，確認題目理解正確。** 這題敘述繞，「移除後綴使 nums 非空」＝
   **枚舉前綴 `nums[start..j]`**（j 從 start 到 n-1）。暴力解 `O(q·n)`，
   三個範例都過 → 理解無誤，再談優化。

2. **找出浪費在哪。** 兩次查詢之間只改了一格，卻整條重掃。
   預先算好前綴積表也不行 —— 改一格，後面整片要重算。
   需求變成「**單點修改 + 區間查詢都要快**」＝ 線段樹。

3. **線段樹的真正難點：節點該存什麼才能合併。**
   只存 `cnt`（前綴餘數計數）不夠。右段的 cnt 是「假設自己從頭算」的結果，
   但它在整段裡前面掛著整個左段：

   ```
   左段 [3,3] (乘積 9)   右段 [4,2] 自己算的前綴餘數 = 4, 3
   整段 [3,3,4,2] 的前綴  36%5=1, 72%5=2   ← 右段每個都被 9 乘過
   ```

   所以每個節點還要存 **`prod` = 這段總乘積 % k**，用來修正右段。

4. **merge**（父 = 左 ⊕ 右）：

   ```
   cnt = L.cnt                            // 只落在左段的前綴：照抄
   for r in 0..k-1:
       cnt[L.prod * r % k] += R.cnt[r]    // 跨進右段的：先乘上整個左段
   prod = L.prod * R.prod % k
   ```

   `k ≤ 5` 是題目給的關鍵提示 —— 每個節點只要 5 格計數，這個迴圈才便宜。

5. **主流程**與暴力解結構相同，只是內層迴圈換成 query：

   ```
   build(1, 0, n-1)
   for [index, value, start, x] in queries:
       update(1, 0, n-1, index, value)        // 永久
       ans = query(1, 0, n-1, start, n-1).cnt[x]
   ```

### 複雜度

- 時間：O(n·k + q·k·log n) ≈ 2e6，對比暴力解 O(q·n) = 2e9，差約 1000 倍
- 空間：O(n·k)。`prod` 開 4n、`cnt` 開 4n·k

開 4n 而不是 2n，是因為 n 不是 2 的次方時遞迴切分會讓樹長歪，2n 可能不夠。

### 踩到的坑

- **merge 不可交換。** 公式裡只用了 `L.prod`，左右地位不對等，
  `merge(A,B) ≠ merge(B,A)`。query 拆成多塊後**必須嚴格由左往右**合併。
  寫反不會 crash，只會默默算錯 —— 這題最難 debug 的坑
- **`cnt[...] += ` 不能寫成 `=`。** 不同的 r 可能被 `L.prod` 乘到同一格
  （`L.prod == 0` 時全部塞進第 0 格），寫 `=` 會被後面的覆蓋
- **查詢累加器的初值要寫 `1 % k`，不能寫 `1`。** k == 1 時餘數只能是 0，
  留著 1 會讓第一次 merge 全錯
- **先取餘再相乘。** `v` 可到 1e9，但 `prod` 早已 < k，`L.prod * r` 最大只有
  `4 × 4 = 16`，不會溢位 int
- **update 只走一條路。** 跟 build 的差別就在「build 兩邊都遞迴、update 只挑一邊」。
  沒走到的子樹不用動，那段本來就沒變

### 驗證

三個官方範例都過。另外與暴力解隨機對拍 4000 組（n ≤ 9、k ≤ 5，含 k=1 與 n=1 邊界），
JS / C++ 皆全數一致。規模 `n=1e5, q=2e4`：

| 解法 | `start=0` | `start` 隨機 |
|---|---|---|
| 暴力 O(q·n)（Python） | 約 426 秒 | — |
| 線段樹（JS / node） | 65 ms | 122 ms |
| 線段樹（C++ -O2） | 24 ms | 36 ms |

**反直覺**：`start=0` 對暴力解是最壞情況，對線段樹卻是**最好**的 ——
`[0, n-1]` 整段就是根節點，query 一次命中「情況B」直接回傳，只碰 1 個節點。
`start` 隨機才要拆成 O(log n) 塊逐一合併，所以真正的最壞情況是 `start` 分散。

拆開量測（JS，n=1e5 / q=2e4）：build 一次 15~22 ms、update 共 28 ms、
query 共 8 ms（start=0）或 30 ms（start 隨機）—— **瓶頸在 update**，
因為它每次都要從根走到葉，不像 query 常能在上層就被整段吃掉。

## 面試官問答

### 1. 為什麼每個節點除了 `cnt`，還一定要存 `prod`？只存 `cnt` 會怎樣？

<details>
<summary>參考答案</summary>

因為 `cnt` 描述的是「這段**自己從頭算**」的前綴餘數。但右子段在父段裡並不是從頭開始，
它前面掛著整個左段，所以每個餘數都要先乘上左段總乘積才是真的。

```
左 [3,3] (乘積 9)   右 [4,2] 自己算的前綴餘數 = 4, 3
整段 [3,3,4,2] 的前綴 = 3, 4, 36%5=1, 72%5=2   ← 右邊貢獻變成 1, 2
```

右段不知道左邊有什麼，修正資訊只能由左段提供，那就是 `L.prod`。
若只存 `cnt`，merge 就變成單純相加 —— 只有在 `L.prod % k == 1` 時碰巧正確。

</details>

### 2. `cnt[L.prod * r % k] += R.cnt[r]` 這行，為什麼是 `+=` 而不是 `=`？

<details>
<summary>參考答案</summary>

因為 `r → L.prod * r % k` 這個映射**不是一對一的**，不同的 `r` 可能落到同一格。
最極端的是 `L.prod == 0`（左段乘出 k 的倍數），此時所有 `r` 全部塞進第 0 格。

```
L = [5,2] → L.prod = 10 % 5 = 0，L.cnt = {0:2}
r=3 → 0*3%5 = 0 → cnt[0] 2→3
r=4 → 0*4%5 = 0 → cnt[0] 3→4     寫成 = 的話只會剩 1
```

只有當 `gcd(L.prod, k) == 1` 時映射才是排列（雙射）。k 可以是 4 這種合數，不能賭。

</details>

### 3. merge 可交換嗎？這對 query 的實作有什麼要求？

<details>
<summary>參考答案</summary>

**不可交換**。公式裡只用了 `L.prod`，沒用 `R.prod`，左右地位不對等，
所以 `merge(A,B) ≠ merge(B,A)`（合理：`[5,2,4,2]` 和 `[4,2,5,2]` 本來就不同）。

但它**可結合**，這才是線段樹成立的條件。實作上的要求是：
query 把區間拆成多塊後，**必須嚴格由左往右合併**。程式碼裡靠
`query(左小孩)` 寫在 `query(右小孩)` 之前來保證。

寫反不會 crash 也不會越界，只會默默算錯 —— 這題最難 debug 的坑。

</details>

### 4. `accProd` 的初值為什麼寫 `1 % k` 而不是 `1`？

<details>
<summary>參考答案</summary>

`accProd` 代表「目前已拼好的那段」，初值要是合併單位元（空段）。一般情況 `prod = 1`
確實是單位元，但 `k == 1` 時所有餘數只能是 0，留著 1 會讓第一次
`accProd * r % k` 算錯，也讓 `acc` 索引超出長度 1 的陣列。

`1 % k` 在 k ≥ 2 時等於 1，k == 1 時等於 0，兩種情況都對。
題目限制是 `1 <= k <= 5`，k=1 是合法輸入，不能不管。

</details>

### 5. 為什麼線段樹陣列要開 `4n` 而不是 `2n`？

<details>
<summary>參考答案</summary>

因為這是**遞迴式**線段樹，節點編號用 `2i` / `2i+1`。當 n 不是 2 的次方時，
遞迴切分會讓樹長歪，最深的葉子編號可能超過 `2n`。

嚴謹的上界是 `2 * 2^⌈log₂ n⌉`（n 略大於 2 的次方時最接近 4n），`4n` 是保險的懶人寫法。
若改用**迭代式**（bottom-up）線段樹，把 n 補到 2 的次方後 `2n` 就夠。

</details>

### 6. `build` 和 `update` 的程式碼幾乎一樣，差別在哪？為什麼沒走到的子樹不用重算？

<details>
<summary>參考答案</summary>

差別只有一行：**build 兩個小孩都遞迴，update 只挑目標所在的那一邊走**。
所以 build 走遍 O(n) 個節點，update 只走一條根到葉的路徑，O(log n) 個。

沒走到的子樹不用動，是因為節點存的值**只取決於它自己負責的那段元素**。
那段沒有任何元素被改，值當然還正確。這也是線段樹能快的根本原因 ——
n=1e5 時 update 只碰 17 個節點，而不是 1e5 個。

</details>

### 7. query 的三種情況中，「完全被包住就直接回傳」為什麼是效能關鍵？

<details>
<summary>參考答案</summary>

因為它讓遞迴**提早剪斷**。一旦節點範圍完全落在 `[l, r]` 內，整段的答案已經算好了，
不必再往下拆到葉子。

```
查 [1..3]：節點3 [2..3] 完全被包住 → 整個拿走，節點 6、7 碰都沒碰
```

數學上，任何區間最多被拆成 O(log n) 塊（每一層最多 2 塊）。
少了這個剪枝，query 會退化成走訪整棵樹 O(n)，跟暴力解一樣慢。

</details>

### 8. 實測發現 `start=0` 比 `start` 隨機**快** 4 倍，為什麼？

<details>
<summary>參考答案</summary>

`start=0` 時查的是 `[0, n-1]`，就是根節點負責的整段，query 第一次呼叫就命中
「完全被包住」，只碰 **1 個節點**。`start` 隨機才需要拆成 O(log n) 塊逐一合併。

實測（JS，n=1e5 / q=2e4）：query 總耗時 8 ms（start=0）vs 30 ms（start 隨機）。

值得注意的是這跟暴力解**正好相反** —— 對暴力解 `start=0` 要掃全陣列，是最壞情況。
出測資時如果只用 `start=0`，會同時低估暴力解、高估線段樹。

</details>

### 9. 這題的時間複雜度還能再降嗎？

<details>
<summary>參考答案</summary>

以一般情況而言**不能再降階**。下界論證：必須讀過每個元素，否則對手可以改動你沒讀到的
那一格，讓答案改變；所以至少 Ω(n)。每筆查詢也至少要花 Ω(1)，所以 Ω(n + q)。
目前是 O(n·k + q·k·log n)，只差一個 log。

實測瓶頸在 **update 而非 query**（28 ms vs 8~30 ms），因為 update 每次都得從根走到葉，
而 query 常在上層就被整段吃掉。

常數層級的改善有：改迭代式 bottom-up 線段樹（省掉遞迴呼叫開銷）、
把 `cnt` 換成位元打包（k ≤ 5，計數上限 1e5 需 17 bits，塞不進單一 64-bit word，效益有限）。
這些都未實測，不宜宣稱有顯著提升。

</details>

### 10. 空間還能再省嗎？要區分哪兩種空間？

<details>
<summary>參考答案</summary>

- **輸出空間** O(q)：題目要求回傳長度 q 的陣列，這是必需的，不計入輔助空間。
- **輔助空間** O(n·k)：`prod` 開 4n、`cnt` 開 4n·k。

能省的都是常數層級：`4n` → `2·2^⌈log₂ n⌉`，或改迭代式線段樹用 `2n`，
最多省一半左右。**未實測速度差異，不宜宣稱變快**。

階數上省不掉：要支援單點修改 + 任意區間查詢，就得存住每段的 `(prod, cnt)`，
而 cnt 本身就有 k 格。另外**不能改用樹狀陣列（BIT）**壓空間 —— BIT 需要可逆運算來做前綴相減，
而這裡的 merge 不可交換、`prod` 為 0 時也沒有反元素。

</details>

### 11. 如果把「移除前綴」改成「任意區間 `[l, r]`」，解法要怎麼改？如果 k 放大到 1e5 呢？

<details>
<summary>參考答案</summary>

**改成任意區間**：幾乎不用改。`query(1, 0, n-1, l, r)` 本來就支援任意區間，
只是題目剛好固定 `r = n-1`。這也是為什麼寫通用的 query 比寫「後綴專用」版本划算。

**k 放大到 1e5**：整個解法垮掉。節點空間變成 O(n·k) = 1e10，merge 也要 O(k)。
`k ≤ 5` 是這個解法成立的前提，題目給這個怪上限就是在暗示「每個節點存計數陣列是可行的」。
k 很大時只能換思路，例如離線處理、或利用「前綴積 mod k 的相異值個數有限」之類的結構性質。

</details>
