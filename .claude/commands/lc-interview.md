針對 LeetCode 題目產生「面試官問答」。目標題目：$1（若為空，取 `daily/` 底下日期最新的那一題）。

## 步驟

1. 用 `ls daily/` 找到目標資料夾，讀取它的 `README.md`（題目與解題筆記）、`meta.json`，
   以及所有 `solution.*` 檔。
2. 依照下面的規則，產生 8 到 12 題問答。
3. 用 Edit 就地改寫 `README.md` 裡「## 面試官問答」那一段的內容
   （只改這一段，不要動到「## 題目」和「## 解題筆記」）。若該段還不存在，加在檔案最後。
4. 回報產生了幾題、涵蓋哪些面向，一到兩行就好。

## 內容要求

**必須基於這一題的實際內容**，不要套用通用面試題。問題要能從這份程式碼與解法推導出來，
使用者答得出來就代表真的懂這題。

**答案裡的事實要查證過**：題號、題名、複雜度、語言特性（型別上限、溢位行為）不要憑印象寫。
效能宣稱必須實際跑過才寫，量測結果落在雜訊範圍就要照實說「差異不顯著」。

每題涵蓋的面向，從下列挑選（不必全部都有，但不要集中在同一類）：

- **複雜度**：時間與空間怎麼算出來的；能不能更好；瓶頸在哪
- **為什麼這樣做**：關鍵設計決策的理由，以及不這樣做會怎樣
- **正確性**：為什麼不會重複計算或漏算；不變量是什麼
- **邊界條件**：空輸入、單一元素、極值、題目限制的邊緣
- **溢位與型別**：數值範圍、該用什麼型別、換個語言會不會出問題
- **變形題**：改動題目條件後解法要怎麼調整（這是面試最常見的追問）
- **取捨**：這個解法跟另一種寫法相比，各自的優缺點
- **能不能更快**（每次都要有一題）：現在的時間複雜度能不能再降？若能，關鍵觀察是什麼；
  若不能，理論下界是什麼、為什麼現在的解法已經到頂。下界論證要具體，例如「必須讀過每個元素，
  否則對手可以改動未讀的元素讓答案改變」「輸出本身就有 k 格」
- **能不能更省空間**（每次都要有一題）：現在的空間能不能再壓？要區分「輸出佔的空間」與
  「額外輸入以外的輔助空間」。如果只剩下微優化（省掉配置、原地修改），要說清楚那是常數層級的差異，
  而且**不要宣稱有效能提升，除非實際量測過**
- **相關題目**（每次都要有一題，放最後）：列出 3 到 5 題同類型或延伸的 LeetCode 題目，
  說明彼此的關聯與難度落差。**題號與題名必須查證過**，不要憑印象寫。可以用
  `python3 lcdaily.py` 同目錄下的 GraphQL 查詢，或直接問使用者要不要你去查

## 格式

每一題用這個結構，問題直接列出、參考答案收在 `<details>` 裡，方便自己先想過再對答案：

```markdown
### 1. <問題>

<details>
<summary>參考答案</summary>

<答案內容，兩到五句，講重點不要長篇大論。可以放程式碼片段或複雜度算式。>

</details>
```

編號從 1 開始連續。問題本身要具體，例如問「為什麼 `next` 要另外開一個陣列，不能直接改 `cur`？」
而不是「請說明你的解法」。

## 用語

台灣繁體中文技術用語（陣列、迴圈、遞迴、雜湊表、指標、字串、時間複雜度）。
程式碼、變數名稱、複雜度表示法保持原樣。不要用中國大陸用語。
